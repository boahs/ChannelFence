# Show HN checklist

## Authorship rule

The final Show HN title and first comment must be written manually by the user. Do not paste generated copy, and do not ask an AI tool to rewrite or edit the final submission. This file is only a factual readiness checklist.

## Account readiness

- [ ] Request a rename from the project-name account to a normal human alias.
- [ ] Do not make the submission from an account presented as the product.
- [ ] Participate normally before submitting. Do not manufacture activity or leave filler comments.
- [ ] If the rename is not resolved by Day 20, skip Show HN during this campaign.

## Product readiness

- [ ] `https://channelfence.app/` is live, fast, and works without an account.
- [ ] The GitHub repository is public and its README links to the Chrome Web Store.
- [ ] The current Store build and public screenshots match.
- [ ] CI, unit, regression, live YouTube, and performance checks pass.
- [ ] Known limitations are documented plainly.
- [ ] GitHub Issues is ready for missing-surface and compatibility reports.

## Facts the user can cover in their own words

- The personal YouTube problem that caused the project to exist.
- What a persistent creator block list means in practice.
- Why YouTube's "Don't recommend channel" did not solve that problem.
- Manifest V3 and local-only storage.
- Problems caused by YouTube's client-side navigation and frequently changing markup.
- Why the project has Playwright regression tests and live YouTube smoke tests.
- What is intentionally out of scope.
- A direct request for reports of YouTube surfaces the extension misses.

Do not force every point into the comment. The useful technical details matter more than a launch pitch.

## Submission window

- [ ] Choose a weekday when the user can monitor the thread for at least four hours.
- [ ] Confirm the domain, Store, and repository are healthy immediately before submission.
- [ ] Use a direct project or repository URL that lets readers inspect the work.
- [ ] Check the current Show HN guidelines again before posting.

## After submitting

- Answer technical questions directly and disclose limitations.
- Correct factual errors quickly.
- Treat bug reports as useful reports, not criticism to fight.
- Do not ask for upvotes, coordinate comments, or direct a group to the thread.
- Do not repeatedly repost because the first submission was quiet.
- Record visits, installs, uninstalls, and support reports in the private campaign log.
